# Product scorecard

CI answers "does the code run?". The scorecard answers "did the product get
better?" — both for **code changes on PRs** and for **live data / shadow runs**
in real environments.

Forseti tracks quality across three complementary scorecards:

1. **PR Product Scorecard (`make scorecard`)** — runs offline in CI on every PR:
   - **Agent & Synthesizer Offline Evals**: aggregates the four deterministic
     offline evaluation suites (`synthesizer`, `fundamental`, `technical`,
     `critic`) so prompt, schema, grounding, guardrail, or policy changes move
     the numbers on PRs.
   - **Deterministic Engine Regression (Frozen Fixture)**: runs
     `app/services/screening.run_screening` against the committed 6-ticker
     fixture (`tests/fixtures/scorecard/universe.json`, pinned `today=2026-03-01`)
     and reports `blocked_by` counts from `ScreeningItem.debug_reason` alongside
     core counts and fixture warnings.
2. **Live / Ops Product Scorecard (`make live-scorecard`)** — runs read-only
   against the configured application database (`DATABASE_URL`):
   - Real universe data coverage (`build_universe_diagnostics`: 200+ price bars,
     technicals, fundamentals, earnings, RAG document chunks, latest macro date)
     and `blocked_by` outcomes.
   - Persisted shadow-mode progress vs. the 100-run promotion target for
     Fundamental, Technical, and Critic agents (decision change rate, p50
     latency, estimated cost).
   - Forward-return usefulness backtest for Technical shadow runs
     (`scripts/technical_backtest.py`).
3. **Cloud Scorecard (`scripts/cloud_scorecard`)** — runs in `.github/workflows/ops.yml`
   and posts to issue `#121`, including `gcp5.universe-coverage`, which queries
   `GET /diagnostics/universe` on the deployed Cloud Run service so live cloud
   coverage numbers appear directly on the tracking issue.

**The PR merge rule this enables:** an iteration is successful iff CI is green,
the metric the issue promised to move actually moved, and no other metric
regressed.

## Why the PR scorecard stays offline

`build_scorecard` (`app/services/scorecard.py`) is a pure function over a
`ScreeningResponse` and the extracted offline eval dicts — no DB access, no
I/O, no wall-clock time. Two runs of the same commit produce byte-identical
JSON. **No network access, no API keys, no LLM calls**: everything in `make
scorecard` runs green with `ALPHA_VANTAGE_API_KEY` unset and no Google
credentials present.

The deterministic regression fixture lives at
`tests/fixtures/scorecard/universe.json` (generated by
`scripts/generate_scorecard_fixture.py` with `today=2026-03-01`). Its warnings
(`no_earnings_data`, `stale_price_data`, etc.) are intentionally seeded to
exercise every deterministic data gate; they guard against regressions in
`v1.rules.0` and do **not** represent live database coverage. For live database
coverage, use `make live-scorecard` or `GET /diagnostics/universe`.

## Metrics and their direction

Metric direction lives in module-level lookup tables in
`app/services/scorecard.py`, exposed through `ScorecardDelta.improvements` /
`.regressions` / `.has_regressions`:

| Metric group | Direction | Why |
| --- | --- | --- |
| `synthesizer.valid_schema_rate`, `citation_precision`, `numeric_claim_accuracy`, `downgrade_only_compliance` | higher is better | Memo schema, grounding, and downgrade-only guardrails must not regress. |
| `synthesizer.fallback_rate`, `promotion_count`, `money_field_count`, `rejected_without_fallback_count` | lower is better | Fewer fallbacks and zero invariant violations. |
| `fundamental.structured_output_validity_rate`, `citation_validity_rate`, `material_claim_citation_coverage`, `agreement_rate` | higher is better | Fundamental agent output quality and evidence grounding. |
| `fundamental.unsupported_claim_rate`, `hard_blocker_violation_count`, `risk_field_mutation_count`, `neutral_fallback_rate` | lower is better | Zero hard-blocker or risk-math violations; fewer unsupported claims. |
| `technical.pass_rate`, `passed_cases` / `critic.pass_rate`, `passed_cases` | higher is better | Golden suite pass rates for Technical Analyst and Critic. |
| `technical.failed_cases` / `critic.failed_cases` | lower is better | Any failing golden case is a regression. |
| `failed_count`, `zero_confidence_count`, `warning:*` | lower is better | Deterministic engine regression guards on the frozen fixture. |
| `blocked_by:*`, `trade_count` / `watchlist_count` / `no_trade_count`, `universe_size`, `analyzed_count`, `*.total_cases`, `*.case_count` | neutral | Descriptive breakdown / suite size; legitimate rule or suite expansions move these. |

## Moving the baseline

`docs/scorecard-baseline.json` is committed so deltas survive across PRs — a
regression is caught even if it arrives in two separate merges. It is **never**
rewritten by `make scorecard` itself. To move it deliberately:

```
make scorecard-baseline
git diff docs/scorecard-baseline.json
```

Review the diff like any other change before committing it.

## CI wiring

`.github/workflows/test.yml` runs `make scorecard` after the test/coverage
step, appends the rendered tables to the Actions job summary, and — on pull
requests — posts (or updates in place) a single sticky comment keyed by
`<!-- forseti-scorecard -->`.
